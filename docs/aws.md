# AWS behavior Duva depends on

Facts about AWS that shaped Duva's design, each with how it was established. A change that relies on one of them, or would undo a choice made because of one, cites it here. When a run or a probe settles a new one, add it.

## Cognito

- **CreateUserPool refuses an SES identity that SES hasn't verified.** With `EmailSendingAccount: DEVELOPER`, it fails with "Email address is not verified". A new domain's identity never is on its first deploy, so the stack takes `DomainVerified`, and until SES has verified the domain the pool sends with `COGNITO_DEFAULT`. _Probed in 925039213717, 2026-10-03._
- **A pool on `COGNITO_DEFAULT` can still offer email OTP sign-in.** Codes then come from `no-reply@verificationemail.com`, which isn't in the account's SES sandbox. _Probed, and signed in through it in eu-west-3, 2026-10-03._
- **Humans created without a password are confirmed at once,** when a passwordless factor such as email OTP is available, and Cognito can't generate a password for them. PASSWORD must still be listed among the first factors. _[Creating user accounts as administrator](https://docs.aws.amazon.com/cognito/latest/developerguide/how-to-create-user-accounts.html)._
- **Choice-based and passwordless sign-in exist only in the newer managed login,** never in the classic hosted UI. An app client needs `ALLOW_USER_AUTH`. _[re:Post, passwordless authentication](https://repost.aws/knowledge-center/cognito-passwordless-authentication)._
- **Callback URLs match exactly, port included.** HTTP is allowed only for `localhost`, `127.0.0.1` and `[::1]`. So `duva login` listens on a fixed port. _[CreateUserPoolClient, CallbackURLs](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html)._
- **A user pool without `UsernameConfiguration` is case-sensitive for sign-in names,** the legacy default, and that can't change in place. In Duva's first pool, sign-in with `RR23Codes@` for a human added as `rr23codes@` started a challenge but sent no code, because user-existence protection hides the unknown name. So #30 replaced it with a pool that sets `CaseSensitive: false`. _Real run of #23._
- **A pool CloudFormation keeps on removal keeps its `aws:cloudformation:*` tags,** stack ID and logical ID included, so deploy finds the pools its stack retired by the stack ID. _Probed with a throwaway stack in eu-west-3, 2026-10-04._
- **DeleteUserPool refuses a pool that has a domain,** with "User pool cannot be deleted. It has a domain configured that should be deleted first." A domain CloudFormation doesn't keep is deleted when it leaves the template, even though its pool is kept. _Probed with a throwaway stack in eu-west-3, 2026-10-04._
- **The API can create a human who signs in at once.** AdminCreateUser with no password, `email_verified` and `MessageAction: SUPPRESS` gave a user who signed in through `USER_AUTH` with `EMAIL_OTP`, with the code sent from the organization's domain. _Real run of #23._
- **UpdateUserPool resets every setting it isn't given,** so changing a pool's sender gives it all the others as DescribeUserPool returns them. Given those, without AdminCreateUserConfig's deprecated `UnusedAccountValidityDays`, it moved a pool from `COGNITO_DEFAULT` to `DEVELOPER` with an SES domain identity and kept its sign-in policy, and it refused an identity SES hasn't verified with "Email address is not verified", as CreateUserPool does. So the API changes the sender when an admin chooses the sign-in domain, and deploy gives the stack the domain the pool has, so a deploy never reverts it. _[UpdateUserPool](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_UpdateUserPool.html); probed with a throwaway pool in eu-north-1, 2026-10-06._
- **Prefix domains are unique per region.** Deployments in eu-north-1 and eu-west-3 of the same account both took `duva-925039213717`. _Real run, 2026-10-03._

## API Gateway HTTP APIs

- **A Lambda authorizer answers 401 by failing with "Unauthorized",** but only when it has no identity sources. With identity sources, API Gateway answers 401 itself when one is missing, and `isAuthorized: false` gives 403. Caching needs an identity source, so Duva's authorizer caches nothing. _[HTTP API Lambda authorizers](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-lambda-authorizer.html); 401 for a missing and a forged token seen in the real run, 2026-10-03._

## CloudFront

- **Names are global to the account.** Two regions' stacks collided on the origin access control's CDK default name, so every CloudFront name carries the region. _Real run, 2026-10-03._
- **An S3 origin with origin access control serves a public path without a public bucket or a Lambda.** The organization's own logos are in a bucket with every public access blocked, whose policy lets only `cloudfront.amazonaws.com` for the web app's distribution `s3:GetObject`, and CloudFront serves them under `/bimi/` with the content type and Cache-Control each object was put with (ADR-0026). Without `s3:ListBucket`, a missing key answers 403, not 404. A response headers policy adds the Content-Security-Policy and `nosniff`. The CachingOptimized policy keeps an object as long as its Cache-Control says, within a day by default. _[Restrict access to an Amazon S3 origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html); not yet seen in a real run._
- **A response headers policy takes security headers only as security headers.** CloudFormation refuses Content-Security-Policy as a custom header ("The parameter CustomHeaders contains content-security-policy that is a security header and cannot be set as custom header"), and the deploy rolls back. The same holds for Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options, X-XSS-Protection and Referrer-Policy, each set through its own part of `SecurityHeadersConfig`, where X-Content-Type-Options is only ever `nosniff`. _Failed deploy of #119, 2026-10-07; [Understand response headers policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-response-headers-policies.html)._

## SES

- **An active receipt rule set with no rules refuses all mail** with `550 5.1.1`. _Real run of #4._
- **SESv2 SendEmail with raw content delivers to every address in `Destination`,** Bcc included, and leaves the raw headers as they are, so a Bcc recipient gets the mail without any header naming them. Only the Message-ID is replaced. _Real run of #25._
- **SES receiving refuses mail from IP addresses on its blocklists** with `550 5.7.1 IP address blacklisted by recipient` at RCPT TO, for every recipient. This machine's home IP was listed after its address changed. _Real run of #23._
- **SES answers each recipient on its own.** In one SMTP transaction, an address no rule lists gets `550 5.1.1` at RCPT TO while a listed one gets `250`, and the message goes to the listed one only. So Duva never bounces. _Probed over SMTP to inbound-smtp.eu-north-1, real run of #7._
- **A rule's address also takes its plus-tagged addresses, in any case.** With `realrun7@duva.nille.xyz` listed, SES took `RealRun7+Probe@duva.nille.xyz`, and the receipt's recipient keeps the case it was sent in. _Real run of #7._
- **SES receiving takes some seconds to pick up a rule's new recipient,** and refuses mail to it with `550 5.1.1` until then. A message Duva sent through SES to a group created 26 seconds earlier bounced that way. That is the one observation; how long it takes at most is unmeasured. _Real run of #72, 2026-10-06._
- **A hard bounce puts the address on the account's suppression list, which then keeps SES from delivering to it.** Account 925039213717 suppresses `BOUNCE` and `COMPLAINT` in eu-north-1 and eu-west-3 (GetAccount's `SuppressionAttributes`). So #72's bounce suppressed the organization's own group, and every later send to it bounced until it was removed by hand. SES accepts a send to a suppressed address and publishes a `Permanent` bounce with the subtype `OnAccountSuppressionList` instead of delivering it. So Duva takes each address its rules start listing off the list, and the feedback Lambda takes off any of the organization's addresses that hard-bounces, and never counts that bounce toward pausing the agent. DeleteSuppressedDestination for an address not on the list fails with `NotFoundException` (404), which Duva takes as done. Listing the list is one call per 1,000 entries, where an alias domain may mirror many addresses, so Duva lists it, then removes only the addresses on it. The list is the account's, so its actions take `Resource: "*"`, which no real run has tried yet. Nor has one shown whether SES suppresses the address before or after it publishes the bounce, which decides whether the feedback Lambda's removal holds; if after, the next send to it bounces as `OnAccountSuppressionList`, and that bounce takes it off. _[Using the account-level suppression list](https://docs.aws.amazon.com/ses/latest/dg/sending-email-suppression-list.html); GetAccount and DeleteSuppressedDestination probed, 2026-10-06; real run of #72._
- **A rule without recipients takes every address on the account's verified domains,** so Duva never writes one. _[ReceiptRule, Recipients](https://docs.aws.amazon.com/ses/latest/APIReference/API_ReceiptRule.html)._
- **A rule recipient that is a domain, like `example.com`, takes every address on it, but not on its subdomains,** which only `.example.com` would. So a domain's catch-all is its domain, and each of its alias domains, listed in Duva's rules while it is set, next to the addresses, which stay where they are, so clearing it never refuses mail to them. Each takes one of the rules' recipients. _[Creating receipt rules](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-receipt-rules-console-walkthrough.html); not yet seen in a real run._
- **A rule takes at most 500 recipients, and a rule set at most 200 rules,** neither adjustable. So Duva spreads the addresses over rules of its own, `Addresses`, then `Addresses-2` and on, each with up to 500. An address stays in the rule that lists it, so changing the rules never refuses mail to it for a moment; a new address goes in the first rule with room, or a new rule; and a rule left with no recipients is deleted, since one without recipients would take every address. That caps an organization at 100,000 addresses, more than ADR-0004's estimate of roughly 20,000. _[SES quotas](https://docs.aws.amazon.com/ses/latest/dg/quotas.html)._
- **Every rule that lists one of a message's recipients runs its actions on the message,** in the rule set's order. So a message to addresses in two of Duva's rules is stored twice under the same key, and the inbound Lambda runs twice, once per rule. Its record of what each mailbox received makes the second run add nothing. Whether the second receipt names only that rule's recipients or all of them, each mailbox gets one copy either way; no run has settled which. _[ReceiptRule](https://docs.aws.amazon.com/ses/latest/APIReference/API_ReceiptRule.html)._
- **`ScanEnabled` defaults to off** when CreateReceiptRule doesn't set it, so Duva sets it. _Probed with a throwaway rule set in eu-north-1, 2026-10-03._
- **SES's scanning marks the standard test strings.** A message with the EICAR test file attached got a virus FAIL and one with the GTUBE string a spam FAIL, while SES still took both with `250` and stored them, so Duva's verdict handling can be checked from outside. _Real run of #8._
- **SES's spam scan can fail mail SES itself sent from the organization's domain.** Of three urgent alert mails Duva sent from `no-reply@duva.nille.xyz` to a mailbox of its own, one, "n@nille.dev paused Real run 45", got `X-SES-Spam-Verdict: FAIL` with SPF, DKIM and DMARC passing, and the other two PASS. So the sender records the ID SES gave each mail it sends from the system address, and the inbound Lambda takes mail from that address with a DMARC pass and that Message-ID as Duva's own, never spam. _Real run of #82, 2026-10-06._
- **A receipt names the sender's DMARC policy only when DMARC fails,** as `dmarcPolicy`: none, quarantine or reject. The guide writes it in lower case and SES's blog in upper case, so Duva ignores case. _[Contents of notifications for SES email receiving](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-notifications-contents.html)._
- **SES heads each message it stores with its verdicts, and a DKIM result for each signature.** The raw copy starts with `X-SES-Spam-Verdict`, `X-SES-Virus-Verdict`, `Received-SPF` and `Authentication-Results: amazonses.com;`, which has one `dkim=pass header.i=@<domain>` per signature (two for mail SES sent: `amazonses.com` and the identity's domain), then `dmarc=`. The receipt's `dkimVerdict` is one status for all of them, so whether a given signature passed, as a one-click unsubscribe needs (ADR-0016), comes from this header. A sender can write its own `Authentication-Results` lower down, so Duva reads only the first. _Raw copy in the mail bucket of a message to realrun11@, real run of #11._
- **SES replaces the Message-ID of a message sent with raw SendEmail** with `<MessageId@region.amazonses.com>`, where MessageId is the ID SendEmail answers with. Duva's own `<uuid@duva.nille.xyz>` never reached the recipient, so Duva records SES's. _Real run of #11, eu-north-1._
- **SendBounce bounces a message SES received, back to its sender, for up to 24 hours after it arrived,** from an address on a verified identity, at most once a second. Duva can only judge a group's sender once SES has accepted the message, so a group refuses mail with SendBounce, with `mailer-daemon@` the domain as BounceSender and a 5.7.1 DSN per group recipient. SES sends it from its own MAILER-DAEMON all the same (see SES SendBounce's From below). Each bounce is claimed in the table first, so a repeated event never bounces twice, and spam is never bounced, since its sender is most likely forged. _[SendBounce](https://docs.aws.amazon.com/ses/latest/APIReference/API_SendBounce.html); real run of #71._
- **SESv2 SendEmail with raw content is authorized as `ses:SendRawEmail`**, on both the identity and the configuration set. With only `ses:SendEmail` on the configuration set, every send failed with "not authorized to perform 'ses:SendRawEmail' on resource '...configuration-set/...'". _Real run of #11._
- **A configuration set's event destination publishes each event to SNS as JSON with `eventType`,** `mail.messageId` (the ID SendEmail answered with) and an object per type: `bounce` with `bounceType` (`Permanent`, `Transient` or `Undetermined`), `bounceSubType`, `bouncedRecipients`, `timestamp` and `feedbackId`; `complaint` with `complainedRecipients`, `timestamp`, `feedbackId` and, if the report has one, `complaintFeedbackType`; and `reject` with only a `reason`. So Duva maps each event to its send by SES's message ID, treats only `Permanent` as a hard bounce, and claims each report by its `feedbackId`, or once per message for a reject. SES needs `sns:Publish` on the topic, which CDK's event destination grants to `ses.amazonaws.com` with the configuration set as `AWS:SourceArn`. _[Contents of event data that Amazon SES publishes to Amazon SNS](https://docs.aws.amazon.com/ses/latest/dg/event-publishing-retrieving-sns-contents.html); not yet seen in a real run._
- **IAM has no resource type for receipt rules or rule sets.** CreateReceiptRule, DescribeReceiptRule and UpdateReceiptRule need `Resource: "*"`; naming the rule set's ARN is denied. So do DescribeReceiptRuleSet and DeleteReceiptRule, which Duva uses since its addresses take several rules. _[Service Authorization Reference for SES](https://docs.aws.amazon.com/service-authorization/latest/reference/list_ses.html); AccessDenied in the real run of #7._

- **SES sends a message to at most 50 recipients, To, Cc and Bcc together.** So the sender fails a draft with more before it reaches SES, and the transaction that counts an agent's send against its limits, with an item per new recipient, stays within DynamoDB's 100 items. _[SES quotas](https://docs.aws.amazon.com/ses/latest/dg/quotas.html); not yet seen in a real run._

## EventBridge Scheduler

- **A one-time schedule, `at(yyyy-mm-ddThh:mm:ss)`, runs once and with `ActionAfterCompletion: DELETE` is deleted after,** so an agent's sends that wait for its limits cost nothing while none wait. The sender creates one per agent and second, named for both, in a schedule group of the stack's own, which deleting the stack deletes with its schedules. The API creates one in the same group per thread set aside in Remind me and second, named for a hash of the mailbox and thread, since a name holds at most 64 characters, and changing or cancelling a reminder leaves the old schedule to run and find the thread no longer due. Scheduler invokes the sender with a role it assumes, whose trust policy names the group's ARN and the account, so the sender needs no resource policy, and the sender and the API pass that role with `iam:PassRole`. Whether Scheduler takes a time already past is undocumented, so the sender never asks for one sooner than 10 seconds ahead. _[Schedule types](https://docs.aws.amazon.com/scheduler/latest/UserGuide/schedule-types.html), [Setting up the execution role](https://docs.aws.amazon.com/scheduler/latest/UserGuide/setting-up.html#setting-up-execution-role); not yet seen in a real run._

## SQS

- **A FIFO queue takes a message whose deduplication ID it was given in the last 5 minutes as sent, and never delivers it.** Each backfill step's task had an ID of the mailbox and step only, so a rebuild within 5 minutes of the last had its steps dropped and stalled at step 1. So each step's ID carries its rebuild's own ID, and any task for a mailbox takes a step that has waited 2 minutes. _[Exactly-once processing](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html); real run of #67, 2026-10-06._

## S3

- **In a versioned bucket a delete without a version ID only adds a delete marker,** and the earlier versions stay. So erasing dropped mail lists the key's versions and delete markers, which needs `s3:ListBucketVersions`, and deletes each by ID, which needs `s3:DeleteObjectVersion`. _[Deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html); in the real run of #8 a dropped message left no version and no delete marker, and in the real run of #28 the eraser did the same for a received copy under `inbound/` and a sent one under `sent/`, with `s3:ListBucketVersions` conditioned on each prefix._

- **So search indexes are in a bucket of their own, without versioning.** LanceDB deletes the files of the versions it prunes, and in the versioned mail bucket each delete would only add a marker, so erased mail's text would stay in S3. _Follows from the fact above; ADR-0007._

## DynamoDB

- **Two transactions on the same item at once can cancel one with `TransactionConflict`,** not `ConditionalCheckFailed`. Two messages arriving together in one mailbox both claimed its feed's next position, and one was cancelled that way, so a feed write retries on both. _Real run of #7._
- **A transaction can't include two operations on the same item.** DynamoDB refuses it with a ValidationException. So a reply that leaves its thread's place unchanged overwrites the thread's label entries, and deletes only those that move. _[TransactWriteItems](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html)._
- **Point-in-time recovery keeps the table's continuous backups for 35 days by default,** and they can't be edited. So a thread Duva erases, with its messages' metadata (subjects, addresses, snippets) and its change feed's entries, can be restored from them for up to 35 days after it was erased, though its raw mail in S3 is gone. _[Point-in-time recovery for DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html)._
- **An erased message's text leaves the search index's files in S3 within a day,** though it leaves search at once. LanceDB deletes a row by marking it, and the row's text stays in its data file until compaction rewrites the file. LanceDB 0.39.0 does that only past 10% of the file's rows deleted, never by merging a file the indexes cover with one they don't, and Node's `optimize()` can't change either. So the eraser's daily run has each mailbox's indexer write every row of the index again, unchanged, build its full-text indexes again and prune every older version. Then no file in the search bucket holds the text or words of a message erased before the run. _#18's spike; local runs of #63._
- **A condition can compare a list attribute with `=`.** A thread is written only if its `labels` list equals the one read, and real DynamoDB evaluates that as DynamoDB Local does: five replies sent at once all joined their thread. _Real run of #9._

## Lambda

- **A function's resource policy holds at most 20,480 bytes.** CDK's HttpLambdaIntegration gives each route a statement of its own by default, and the API Lambda's 47 came to 19,299 bytes, so #69's four new routes failed the deploy, which rolled back. So the API Lambda has one permission, for `apigateway.amazonaws.com` with the API's own ARN, `<apiId>/*/*/*`. _Failed deploy of #69, 2026-10-06; [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)._
- **An event source mapping's filters are ORed, up to 5 of them,** so one mapping on the table's stream hands the sender both approved drafts and urgent alerts to mail, each record once, in the stream's order. _[Control which events Lambda sends to your function](https://docs.aws.amazon.com/lambda/latest/dg/invocation-eventfiltering.html)._
- **A Lambda permission compares its source ARN with `StringLike`,** so one permission with `receipt-rule/Addresses*` lets SES invoke the inbound Lambda for each of Duva's rules, and the mail bucket's policy does the same with `ArnLike`. _[AddPermission, SourceArn](https://docs.aws.amazon.com/cli/v1/reference/lambda/add-permission.html)._
- **A function URL in `RESPONSE_STREAM` mode can answer with up to 200 MB,** where a buffered answer, as through API Gateway, stops at 6 MB. Past the first 6 MB the stream's bandwidth is capped. So attachments download from a function URL that streams, not through the API. _[Response streaming for Lambda functions](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)._
- **A streamed answer's status and headers go out with the first write.** `awslambda.HttpResponseStream.from(stream, { statusCode, headers })` holds them until something is written, and `stream.end(body)` skipped them, so the function URL answered 502 to every link. Writing the body, then ending the stream, sends them. _Real run of #26, checked by invoking the function with response streaming._
- **The test account strips any Lambda permission anyone may use.** Its security mitigation (`EpoxyAccessRole/...epoxy-mitigations-prod+LambdaFunctionPolicyBlockPublic` in CloudTrail) called RemovePermission on both of the download Lambda's public statements 13 minutes after deploy, and its function URL, with `AuthType NONE`, then answered 403. So no Lambda may be world-invocable: download links go to the web app's CloudFront distribution under `/download/`, which signs each request to the function URL with origin access control, and the URL has `AuthType AWS_IAM`, with a policy that names only `cloudfront.amazonaws.com` and the distribution's ARN. CDK's `FunctionUrlOrigin.withOriginAccessControl` adds only `lambda:InvokeFunctionUrl`, and CloudFront's guide asks for `lambda:InvokeFunction` too, so the stack adds that. _Real run of #26; [Restrict access to a Lambda function URL origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-lambda.html)._
- **Origin access control for Lambda needs a payload hash only for a body.** A viewer's `POST` or `PUT` must carry the body's SHA-256 in `x-amz-content-sha256`, since Lambda takes no unsigned payload. A download is a `GET`, which needs none. _[Restrict access to a Lambda function URL origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-lambda.html)._

- **A Lambda outside a VPC reaches the internet and resolves DNS without a NAT gateway,** with the resolver Lambda gives it, so the inbound Lambda looks up senders' DMARC and BIMI records (TXT `_dmarc.<domain>` and `<selector>._bimi.<domain>`) itself, through `node:dns`, and the logo fetcher Lambda fetches each logo and mark certificate over https, as the unsubscriber does its POST (ADR-0006, ADR-0023). The logo fetcher, like the unsubscriber, has no environment, no permissions and no resource policy, and only the inbound Lambda may invoke it, through IAM, so a URL in someone's DNS reaches nothing of Duva's. Each fetch goes only to port 443 at an address that is public once resolved, gives up after 5 seconds, and takes at most 128 KB, a logo at most 32 KB. _Not yet seen in a real run._

- **A line in embedded metric format that a Node 24 Lambda writes to stdout becomes a CloudWatch metric,** with the function's default Text log format. The inbound Lambda's drop line showed up as `Duva/DroppedMessages{Reason=virus}` within a few minutes. The day's count for 2026-10-04 includes that one probe. _Real run of #31._
- **LanceDB's native module loads in Lambda,** on `nodejs24.x` as an x64 zip and as an arm64 container image, and answers a full-text query from a table on S3 there. _Search spike, #15, 2026-10-03._
- **Only x64 fits a zip.** A zip's unzipped limit is 262,144,000 bytes. LanceDB 0.39.0 with its x64 native module and Apache Arrow takes 213.8 MB, which leaves about 48 MB for Duva's own code. The arm64 native module alone is 389 MB, so arm64 needs an image. _Search spike, #15, 2026-10-03; [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)._
- **LanceDB 0.39.0's IVF_PQ at its defaults finds half of a flat scan's top 20** of Titan vectors (0.50 on 315 queries over 100,000 messages), and probing 40 partitions instead of 20 adds nothing, so the loss is PQ's quantization. IVF_RQ with a refine factor of 5 finds 0.98, filtered or not, and builds in under a second where IVF_PQ took 47 s. _#62, `spikes/search/harness/recall.ts`, results/62-recall.json._
- **LanceDB 0.39.0's hybrid search scales each side's scores to between 0 and 1 before its reranker sees them,** so a reranker can't tell a near meaning from a far one, and a hybrid search whose distance range leaves the vector side empty fails with "expected column _distance not found in rank". A distance range on a vector search with IVF_RQ is applied to the index's rough distances, before refining, and lost every near message in a test. So Duva runs the words and the meaning as two searches at once, as LanceDB runs a hybrid's, cuts the far meanings after refining, and fuses the two by RRF itself. _#62, in the behavior suite._
- **LanceDB 0.39.0's full-text index stems Danish, as `language: "Danish"`.** It finds "regningerne" from "regning" and "beløbet" from "beløb", which Swedish and English stemming leave apart. _#67, probed on local disk._
- **A cold start costs more than its Init Duration.** Seen by the caller, cold invocations of the 213.8 MB x64 zip took about 620 ms longer than init plus handler time, and of the arm64 image about 160 ms. _Search spike, #17, 2026-10-04, 1,080 cold starts._
- **With LanceDB, the arm64 image inits faster than the x64 zip:** about 0.6 s to 0.8 s at every memory size from 1,769 to 10,240 MB. _Search spike, #17, 2026-10-04._

## Bedrock

- **Titan Text Embeddings V2 runs on demand in eu-north-1,** at $0.000021 per 1,000 input tokens, so mail embedded with it stays in the region. A message's subject and the first 2,000 characters of its body average 261 tokens, which makes 100,000 messages cost $0.55. It takes one text per request; 64 concurrent requests from one client ran at about 13,000 a minute without throttling. _Search spike, #16, 2026-10-03; AWS Price List._
- **So Duva embeds each message once, at indexing, for about $0.55 per 100,000 messages,** and the deploy that brings meaning (#62) embeds a mailbox's existing mail in its backfill at the same price. Each search embeds its words, about $0.0000002. Search and the indexer call Titan in the deployment's own region, with `bedrock:InvokeModel` on that one model and nothing else. Titan V2 is listed in eu-north-1, eu-west-1, eu-west-3, eu-central-1 and us-east-1, and Amazon's own models need no Marketplace agreement. _Price from the fact above; ListFoundationModels, 2026-10-06._
- **Titan's cosine distances are near together.** On the spike's 100k mailbox, #19's questions were a median 0.59 from the message each asks about and 0.91 from the median message, and in Duva's test fixtures a paraphrase can be 0.73 from its message and still be the nearest. So search finds by meaning only the 20 nearest within 0.8. _#62, from the exported benchmark vectors and the recorded fixtures._
- **Titan V2's 256 and 512 dimensions are prefixes of its 1,024.** At a smaller size it returns the first components of the 1,024 vector, renormalized (cosine 1.0 against direct requests). So a stored 1,024 vector can be cut to a smaller size later without embedding again. _Search spike, #19, 2026-10-04._
- **Titan doesn't match words across languages.** On #67's made-up evaluation set, a word and its match in the other of English and Swedish were a median 0.85 apart, and the nearest unrelated message 0.86, so no cutoff lets the one in and keeps the other out. ## CloudFront to a function URL, for a POST

- **Origin access control signs the request with its own `Authorization` header,** replacing the viewer's, so a human's access token reaches the conversation Lambda in `x-duva-token` instead. For a POST the viewer also sends the body's SHA-256 in `x-amz-content-sha256`, since Lambda takes no unsigned payload. The behavior's origin request policy forwards only those two and `content-type`, never `Host`, which the signature names. _[Restrict access to a Lambda function URL origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-lambda.html); check-deployment.ts posts a turn with a forged token through it and expects 401, which no real run has seen yet._
- **CloudFront gives up on an origin that sends nothing for its read timeout, 60 seconds at most by default,** which a model thinking between tool calls could reach. So the conversation Lambda writes an empty line every 20 seconds while a run goes. _[Origin response timeout](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html#DownloadDistValuesOriginResponseTimeout); not yet seen in a real run._
