# Search with LanceDB on S3

Keyword, vector and hybrid search run in an embedded LanceDB table per mailbox, stored in the organization's S3 bucket, so idle cost is S3 storage. OpenSearch Serverless was the managed alternative, but a steady trickle of mail keeps it awake at about $190-370 a month per organization. LanceDB is pre-1.0, so a spike (#2) measured it first on a 100k-message mailbox, from Lambda in eu-north-1 (`spikes/search/REPORT.md`). With LanceDB 0.39.0 and its vector index, every target holds at 10,240 MB, in an x64 zip and in an arm64 image. At 1,769 and 3,538 MB every target holds except cold p95, which reaches 3.1 to 3.5 s against 3 s. So search runs in a Lambda with 10,240 MB, packaged as an x64 zip, which `duva deploy` ships as it ships every other Lambda. The arm64 image starts faster when cold, at 2.0 to 2.2 s, but deploy would have to build and push an image to ECR in every organization's account. Nicklas chose the zip on 2026-10-04.

## Consequences

- Search sits behind one module, so the engine can be swapped, and the spike's behavior suite is the contract any engine passes.
- Mail is embedded with Titan Text Embeddings V2 at 1,024 dimensions, which runs in eu-north-1, so mail need not leave the region. It costs $0.55 per 100k messages.
- LanceDB's x64 native module takes about 214 MB with Apache Arrow, which fits a zip with about 47 MB to spare. Its arm64 module is 389 MB, so arm64 needs a container image.
- The zip's cold p95 is 2.7 s against the 3 s target, and its caller sees cold starts of 3.1 to 3.3 s. The margin is thin, so the cold target is measured again whenever the vector index's tuning, LanceDB's version or the package changes, with `node harness/harness.ts benchmark <version>`. If it fails, the arm64 image is the next step, then a search warm-up when someone opens the app. Spec #60 asked for a warm-up anyway, before either: the web app warms search when its search box gets focus (#64).
- At 10,240 MB a search costs two to three times what it does at 1,769 MB, about $2.20 a month for 1,000 searches a day with one in ten cold, against $0.80.
- Semantic search needs the vector index: a flat scan takes about 5 s. At LanceDB's defaults the index finds 0.59 of a flat scan's top 20, so it gets tuned before semantic search ships. #62 tuned it: IVF_RQ with a refine factor of 5 finds 0.98 on the spike's 100k mailbox, and builds in seconds, so compaction builds it again too. LanceDB 0.39.0's own hybrid search scales the vector side's distances before its reranker sees them, so it can't leave out unrelated mail. So Duva runs the words and the meaning as two searches of the same table at once, as LanceDB's hybrid does, and fuses them by RRF itself (docs/aws.md). Measured again then with the spike's benchmark, the zip's cold p95 is 2.57 to 2.70 s and its warm p95 171 to 241 ms, so every target still holds, with the same 0.3 s to spare.
- Each mailbox has one writer, which batches what has arrived, retries, and runs maintenance itself between writes. Readers check for new versions on every search, so new mail is searchable on the next one.
- A removed message's text stays in its S3 data file until compaction rewrites the fragment, which LanceDB does only past 10% of its rows deleted. So erasure deletes the rows at once, which hides them from every search, and the eraser's daily run rewrites every fragment with deleted rows and prunes old versions. An erased message's text leaves S3 within 24 hours. Nicklas chose this on 2026-10-06 over rewriting at every erasure, which would slow Empty Trash on large mailboxes. LanceDB can't be made to rewrite only those fragments, so the run rewrites the whole index of each mailbox with deleted rows and builds its full-text indexes again (`docs/aws.md`, #63).
- Swedish mail is found less well by meaning than English: MRR 0.13 against 0.38 on the spike's templated Swedish mail. Real Swedish mail showed that within a language Titan does well, but across languages it doesn't: "kvitto" missed an English receipt. Titan puts a word and its match in another language about as far apart as unrelated mail, so no cutoff helps (#67).
- So each search is also translated into the organization's search languages, by Amazon Nova Lite in the deployment's own region, so the words stay there. Nicklas chose this on 2026-10-06, as an organization setting admins change: English and Swedish by default, and Danish. Each language adds a Nova Lite call, a Titan embedding and two searches of the index, all at once, and a translation's meaning reaches less far than the search's own, so unrelated results stay few. Mail in each language on the list is indexed with its stemmer, so adding or removing one other than English and Swedish rebuilds every mailbox's index, embedding its mail again at $0.55 per 100k messages. The deploy that brings them rebuilds every index once too, since each now has columns for Danish (index version 3). Measured with the spike's benchmark, a search translated into three languages takes 740 ms at warm p95, against 800, and 3,002 ms at cold p95, which misses 3 s by 2 ms; its caller sees 3.6 s cold (results/67-latency.json). A warm search takes about 0.5 s longer than an untranslated one. The #64 warm-up hides the cold miss for the web app, but an agent's first search after idle feels it. In the same run, keyword searches, which aren't translated, had a cold p95 of 3,896 ms from four slow starts in one batch of ten, against 2,566 in #62's run. One Nova Lite call for all the languages was measured and rejected (#87): it made cold p95 2,837 ms but warm p95 909 ms, against 800, and warm searches are every search, while cold ones are rare and the warm-up hides them for the web app (docs/aws.md).
- Fallback: per-mailbox SQLite FTS5 files in S3 for keywords, plus S3 Vectors for semantic search, merged in our code.
